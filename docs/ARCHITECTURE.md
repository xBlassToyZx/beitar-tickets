# ארכיטקטורה

## שכבות

```
UI (React, src/components)  →  API routes (src/app/api)  →  services (src/server)  →  Prisma  →  SQLite
                                         ↑
                         domain (src/domain): pure logic, shared by all layers
```

- **domain** – לוגיקה טהורה בלי I/O: הגדרת הגושים וקיבולת כל גוש, חלוקה לשורות, קטגוריות ומחירים, חוקים עסקיים. קל לבדוק אותה בבדיקות יחידה, והיא מקור האמת היחיד למבנה האצטדיון. גם ה-seed וגם ציור המפה קוראים ממנה.
- **server** – שירותים שמקבלים את ה-Prisma client כפרמטר (`db`). ככה הבדיקות מריצות את אותו קוד בדיוק מול מסד נתונים זמני.
- **API routes** – שכבה דקה: ולידציה עם Zod, זיהוי הקונה, קריאה לשירות, ותרגום שגיאות ל-JSON דרך `handle()`.
- **UI** – דפי Server Components טוענים נתונים ישירות מהשירותים. רכיבי Client (בחירת מושבים, רכישה) מדברים עם ה-API.

## מניעת מכירה כפולה

זו הדרישה הקריטית במערכת כרטיסים, והיא נאכפת ברמת מסד הנתונים ולא רק בקוד:

1. **שמירה זמנית (`SeatHold`)** – בחירת כיסא יוצרת שמירה ל-10 דקות (`SEAT_HOLD_MINUTES`). אינדקס ייחודי על `(matchId, seatId)` מבטיח ששני קונים לא יכולים לשמור את אותו כיסא. שמירות שפג תוקפן נמחקות בבקשה הבאה למשחק.
2. **תשלום (`checkout`)** – טרנזקציה אחת: בודקת שהשמירות של הקונה עדיין בתוקף, יוצרת הזמנה וכרטיסים ומוחקת את השמירות.
3. **אינדקס ייחודי על `Ticket(matchId, seatId)`** – רשת הביטחון האחרונה: גם אם שתי בקשות עוברות את הבדיקות באותו רגע, רק אחת תצליח לכתוב. השנייה מקבלת `SEAT_TAKEN`.
4. **מנויים** – `SeasonTicket` ייחודי לפי `(season, seatId)` ו-`(season, buyerId)`. כיסא של מנוי חסום בכל המשחקים של העונה.

הבדיקות ב-`tests/integration/booking.test.ts` מכסות את כל המקרים האלה.

## זיהוי קונה

אין עדיין משתמשים והתחברות. `middleware.ts` נותן לכל דפדפן מזהה אנונימי בעוגיית `httpOnly`, וכל השמירות והכרטיסים מקושרים אליו. כשתתווסף התחברות, צריך להחליף את `getBuyerId()` במזהה המשתמש ולשייך כרטיסים קיימים.

## זמינות

הזמינות לכל גוש = קיבולת − כרטיסים שנמכרו − שמירות בתוקף − מנויים. היא מחושבת בשאילתות `groupBy` על עמודת `sectionId` שנשמרת בכפילות בטבלאות `Ticket`, `SeatHold` ו-`SeasonTicket`, כדי לא לחבר לטבלת המושבים (31 אלף שורות) בכל בקשה.

## מסד נתונים

SQLite מתאים לפיתוח ולפרויקט בהיקף הזה. כדי לעבור ל-PostgreSQL בפרודקשן:

1. לשנות את `provider` ב-`schema.prisma` ל-`postgresql`.
2. להחליף את ה-adapter ב-`src/server/prisma.ts` ל-`@prisma/adapter-pg`.
3. ליצור migration חדש עם `prisma migrate dev`.

## מה חסר למוצר אמיתי

- התחברות משתמשים ואימות זהות
- סליקה אמיתית (ספק תשלומים) במקום התשלום המדומה
- ממשק ניהול למשחקים, מחירים וגושים
- שליחת כרטיסים במייל, החזרים והעברת כרטיסים
- הגבלת קצב בקשות (rate limiting) ל-API
- ניטור ולוגים
